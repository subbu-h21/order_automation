# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Internal tool for Shubhada Pharma to automate supplier reordering. It scrapes each supplier's Saved PO reorder suggestions from the CRM, merges them into one curated product list, then searches, matches, and prices every item across the DRK Enterprises / A.K.Pharma / Mahaveer distributor catalogs on Retailio — picking the best-matching product per supplier (dosage-aware, not just text-similarity) and working out a default suggested split per the discount/scheme rules. This is presented as an editable **proposal** for the pharmacy owner to review — full control to change quantity, switch supplier, or pick a different matched product per item — and only once the owner explicitly confirms does the tool go back and actually add the confirmed selections to each distributor's real cart. The review gap can be hours or days (the pending proposal survives a server restart); nothing is added to a cart before that explicit confirm.

Stack: React + Vite + TypeScript frontend, Python + FastAPI + Uvicorn backend, Playwright automation (drives a real, visible Chrome window against the CRM and Retailio — this is not headless scraping, it's UI automation against two external sites that don't have APIs).

## Commands

Day-to-day development (run backend and frontend separately so the frontend hot-reloads):

```bash
cd order_automation_v2 && venv\Scripts\activate && python -m uvicorn app:app --app-dir ..\dashboard\backend --host 0.0.0.0 --port 8000   # API on :8000, reachable from other devices on the LAN
cd dashboard\frontend && npm run dev                                                                                       # Vite dev server, proxies to :8000
```

Frontend (`dashboard/frontend`):
- `npm run dev` — Vite dev server
- `npm run build` — `tsc -b && vite build` (type-checks then builds; this is also what `start.bat` runs before launching the backend)
- `npm run lint` — oxlint
- `npm run preview` — preview the built dist

There is no test suite (frontend or backend) and no backend lint/format command configured.

Production-style run: `start.bat` builds the frontend, starts the backend in its own window (serving both the API and the built frontend from one FastAPI process on :8000), and opens the browser once ready. `setup.bat` does first-time machine setup (Python 3.11 venv, pip install, `playwright install chromium`, `.env` scaffolding, `npm install`).

First-time/new-machine setup requires **Python 3.11 specifically** (`py -3.11`) — newer versions can lack prebuilt wheels for Playwright/pandas. See [README.md](README.md) for full setup steps and the required `.env` variables (`CRM_USERNAME`, `CRM_PASSWORD`, `CRM_USERNAME_SHIVAJI_CHOWK`, `CRM_PASSWORD_SHIVAJI_CHOWK`, `CHROME_PROFILE_DIR`, `SESSION_SECRET_KEY`, `DASHBOARD_USERS`). The last two gate dashboard login (see Authentication below) — without them, `config.py` fails to import at all (fail-fast, deliberate).

## Architecture

### Pipeline (order_automation_v2/) — two independently-triggerable phases

The pipeline is split into two phases sharing one global, single-run-at-a-time backend state (`dashboard/backend/app.py`), moving through the stages `idle → building_proposal → proposal_ready → confirming → confirmed`. Nothing is added to a real cart until the owner explicitly confirms — Phase A only searches/matches/prices and proposes.

**Phase A — "Build proposal"** (`_run_build_proposal`, triggered by `POST /fetch-order`):
1. **`retailio.ensure_logged_in`** — opens a visible tab on the persistent Chrome profile (`CHROME_PROFILE_DIR`) and confirms the Retailio session is valid. If not, it waits (up to 10 min) for a human to complete login/OTP manually in that window — this is intentional, not a bug to route around.
2. **`crm.fetch_orders_for_supplier`** (per `config.CRM_SUPPLIERS` entry) — logs into the CRM, opens the Saved PO / Re-Ordering screen, and scrapes the reorder suggestion table for that vendor into a DataFrame, written to `order_automation_v2/output/<SUPPLIER>_orders.xlsx`. `CRM_SUPPLIERS` is the CRM's own 3 vendor accounts (DRK / A.K.Pharma / Mahaveer) — the CRM has no concept of the Retailio-side distributor split described below, so this list must stay at 3 entries even though `SUPPLIERS` (used from step 4 onward) has 4.
3. **`curated_list.build_curated_list`** — reads those per-vendor Excel files back off disk (iterating `config.CRM_SUPPLIERS`) and merges them into one deduplicated product list (by cleaned product name, taking the max `Required Qty` if the same product appears for multiple vendors). Returns just `product_name`/`required_qty` per item — everything else is initialized by the functions below, so there's nothing else worth pre-seeding here.
4. **`retailio.open_supplier_tab`** (per `config.SUPPLIERS` entry) — opens one Retailio tab per distributor, ticking the distributor checkbox(es) in `config.SUPPLIER_DISTRIBUTOR_NAMES` and running the distributor-specific search view.
5. **`allocate.build_proposal`** → **`gather_candidates`** + **`propose_allocations`** — the core business logic (see below). For each curated item, searches *every* supplier unconditionally (not just until fulfilled — the owner needs to see every option, not just the one the algorithm would have picked) and works out a default suggested split. Never touches a cart.
6. The result is persisted (`order_automation_v2/proposal_store.py`, a flat `output/proposal.json` — no DB) and returned as JSON via `/status` for the dashboard's editable review screen. Persisting to disk (not just in-memory `_state`) is what lets a pending review survive a backend restart — the owner may take hours or days to get back to it.

**Phase B — "Confirm & place orders"** (`_run_confirm`, triggered by `POST /confirm-order`, any time later — possibly a different browser session entirely):
1. Fresh `retailio.ensure_logged_in` + fresh `retailio.open_supplier_tab`s — nothing from Phase A's session (page objects, card indexes) can be reused, since the gap could be long. No CRM step here at all — Phase B only touches Retailio.
2. **`allocate.commit_selections`** — takes the owner's final edited selections (one entry per product, each with the specific supplier/matched-product/qty line(s) they approved) sent in the `/confirm-order` request body. Re-searches each line fresh and matches it by exact product name (`retailio.search_all_offers`); if a confirmed pick can no longer be found (delisted/renamed since Phase A), that line is logged and left unfulfilled rather than fuzzy-rematched or substituted. Calls `retailio.select_and_add_to_cart` for everything it does find. **Every per-line failure is caught and logged inside this loop, never allowed to abort the rest of the run** — since earlier lines in the same call may have already been added to a real cart, letting one flaky line raise up through `_run_confirm` would revert `stage` back to `proposal_ready` inviting a retry, and retrying would blindly resubmit the *same* selections, re-adding everything already-committed a second time. This is the one thing to preserve carefully if `commit_selections` is ever touched.
3. Writes `order_automation_v2/output/allocation_report.xlsx` (3 sheets: Allocations / Unfulfilled / NeedsReview) via `_build_result`/`_write_excel_report` in `app.py` — these two functions are unchanged from before this phase split; `commit_selections` deliberately returns data reshaped into the same item structure they've always consumed (including passing `low_confidence_matches` through from the confirmed selection unchanged, rather than dropping it, so the final report keeps that audit trail). For the same reason as above, a failure in *this* report-writing step (after `commit_selections` has already returned - meaning every real cart-add already happened or was genuinely attempted) still lands `stage` on `confirmed`, never back on `proposal_ready` - only a failure *before* `commit_selections` returns (login, opening tabs) is genuinely safe to treat as retryable.

### Allocation logic (`order_automation_v2/allocate.py`)

This is the part most likely to need care when changed — it encodes real business rules, not just plumbing. `_best_offer`-era logic is now split across the two phases:

- **`gather_candidates(pages, item)`** (Phase A) — searches all 4 suppliers in `config.SUPPLIERS` (DRK → A.K.Pharma (Outstation) → A.K.Pharma (Davangere) → Mahaveer) via `retailio.search_all_offers`, scores every in-stock card against the CRM product name via `matching.is_confident_match` (similarity + dosage-conflict veto + a "rescue path" for pack-size phrasing differences — see `order_automation_v2/matching.py`), and records **every** candidate (confident or not) into `item["candidates"][supplier]` — the owner can deliberately pick a flagged low-confidence match in the review UI if they judge it's actually right. A supplier with no confident candidate at all still gets its best near-miss logged to `item["low_confidence_matches"]`.
- **`propose_allocations(item)`** (Phase A, pure — no Playwright) — runs over the already-gathered candidates to produce a **default suggested split** (`item["proposed_allocations"]`), using the exact same priority + scheme rules this pipeline has always used: the winner is normally the highest-priority supplier with a confident match, *unless* a lower-priority supplier has a scheme (`has_scheme`) that's `_scheme_worth_switching_for` the remaining quantity (`SCHEME_STRETCH_LIMIT` / `MIN_QTY_TO_STRETCH` — don't change these constants without confirming the intended business rule with the user). Only the single best-scoring candidate per supplier is ever proposed automatically per round — same long-standing gap as before, except now the owner can manually add a different candidate from the same supplier in the review UI if the top one's quantity is capped.
- **`commit_selections(pages, selections)`** (Phase B) — executes whatever the owner actually confirmed, described above. The offer returned by `retailio.select_and_add_to_cart` gives the *actual* quantity added (may be less than requested, or 0 — see below); that's what decrements the line's contribution to `remaining_qty`, not the requested amount.
- **Hidden per-order quantity limits**: Retailio enforces `minSaleQty`/`maxSaleQty`/`minimumOrderQuantity` per batch via Angular (`ng-disabled` on the "Add to Cart" button) but never displays them on the card — only the total stock (`Qty N`) is shown, and the site itself does *not* stop you from requesting more than that. `select_and_add_to_cart` reads the real values live from Angular's scope (`_wait_for_full_inventory`, `_capped_qty` in `order_automation_v2/retailio.py`) before filling the quantity box, and clamps/rounds accordingly — a value of `0`/`null` on any of these three fields means "not set" (confirmed empirically across ~20 products on all 3 real suppliers), only a positive value is a real constraint. The button becomes visible in the DOM *before* Angular finishes populating this data async, so `_wait_for_full_inventory` polls (up to 6s) for the full object rather than reading it once — reading too early silently looked like "no limit" and reproduced the original bug this whole mechanism was built to fix. If the real limit still can't be confirmed in time, the offer is skipped (logged via `on_progress`) rather than assumed unlimited. This is only ever discovered for real at Phase B commit-time — Phase A's proposal only shows the visible `Qty N` stock number, so a proposed quantity is provisional until actually committed.

### Playwright layer (`order_automation_v2/crm.py`, `order_automation_v2/retailio.py`)

Both modules are pure Playwright locator/selector code against two live external sites with no API — brittle by nature. Selectors are XPath/CSS tied to the current CRM and Retailio DOM; if scraping or cart-adding starts failing, suspect the external site's markup changed before suspecting the allocation logic. `order_automation_v2/retailio.py`'s card parsing (`_parse_card`) depends on Retailio's product-card text format (`Qty N`, `Scheme: N+M`, and — confirmed live — `MRP:`/`PTR:` lines each followed by a `₹`-prefixed value on the next line) — check a live card's `inner_text()` output before changing these regexes. MRP (regulated retail price, ~fixed regardless of supplier) and PTR ("price to retailer", what the pharmacy actually pays and the number that genuinely differs between suppliers) are both parsed straight off the list card — no need to open the product modal for pricing.

### Backend (dashboard/backend/app.py)

Single-file FastAPI app holding one global `_state` dict (guarded by `_lock`) representing the one-run-at-a-time, two-phase pipeline: `running`, `phase`, `log`, `done`, `result`, `error`, `started_by`, plus `stage` (`idle`/`building_proposal`/`proposal_ready`/`confirming`/`confirmed` — authoritative for which action is currently valid), `proposal` (Phase A's output: `{proposal_id, items}`), and `confirmed_by`. This state is shared by every client that hits the server - not per-session, per-tab, or per-device - which is what makes the multi-viewer behavior below work.

Unlike before, there **is** persistence for the one thing that needs to survive a restart: `order_automation_v2/proposal_store.py` writes the pending proposal (and, once Phase B finishes, its confirmed result) to a flat `output/proposal.json` — still no real DB, just a JSON file, matching how every other piece of config in this project (credentials, branch list) is hand-managed. `_load_persisted_proposal()` reads it once at module import time to reseed `_state`, and `_persist_state()` writes it back after each phase finishes (or clears it once nothing is pending). Everything else about `_state` still resets on every `/fetch-order` call, same as before.

Endpoints:
- `POST /fetch-order {branch}` — starts Phase A in a background thread. Refused (with a `reason`) if a run is already active (`already_running`), or if a proposal is currently pending review (`proposal_pending` — don't silently blow away an unreviewed proposal). Branch selects which CRM credentials from `config.BRANCHES` to use.
- `POST /confirm-order {selections}` — starts Phase B in a background thread with the owner's final selections. Only valid when `stage == "proposal_ready"` and nothing else is running.
- `POST /discard-proposal` — clears a pending proposal (only valid when `stage == "proposal_ready"`) so a fresh `/fetch-order` isn't blocked.
- `GET /status` — full state snapshot; every open frontend tab/device polls this every 1.5s continuously (see Frontend below), not just the one that triggered a run — this is also how a reviewer who opens the dashboard hours or days later sees the same pending proposal.
- `GET /branches` — available branches + default, for the branch picker.
- Static file mount at `/` serves `dashboard/frontend/dist` (the built frontend) — this is why `start.bat` builds the frontend before starting the backend, and why the backend `sys.path`-inserts `order_automation_v2` at import time rather than that being an installed package.

All of `/fetch-order`, `/confirm-order`, `/discard-proposal`, `/status`, `/branches` require the session via `get_current_user`, same as before — easy to forget on a newly-added endpoint, worth double-checking whenever one is added.

`start.bat`/the dev uvicorn command bind to `--host 0.0.0.0` (not the default `127.0.0.1`-only) specifically so other devices on the same LAN (e.g. a phone) can reach it. The dashboard is also reachable from the public internet via a Cloudflare named tunnel (configured outside this repo, in the Cloudflare Zero Trust dashboard, routing a public hostname to `localhost:8000`) - see Authentication below for how access is actually restricted, since neither of those alone gates who can use it.

### Authentication (`order_automation_v2/auth.py`, `dashboard/backend/app.py`)

Individual staff accounts, provisioned by hand-editing `.env` (no DB, no admin UI, no self-signup - matches how `CRM_USERNAME`/`CRM_PASSWORD`/etc. already work in this codebase). Generate a new account's credential with `python hash_password.py` (prompts via `getpass`, never plain CLI args - avoids leaking passwords into shell history) and paste the printed `salt$hash` into `DASHBOARD_USERS` in `.env` as `username:salt$hash` (comma-separated for multiple staff).

- **Password verification** (`auth.verify_password`): `hashlib.pbkdf2_hmac`, 600k iterations, stdlib only (no bcrypt/passlib). Always runs one PBKDF2 pass even for an unknown username (against a precomputed dummy salt/hash) and always compares with `hmac.compare_digest` - skipping either of those turns response timing into a way to enumerate valid usernames.
- **Brute-force protection** (`auth.check_rate_limit`): in-memory, per-*username* (5 failed attempts / 5 min → `429`), not per-IP. IP-based limiting doesn't work here - `cloudflared` proxies tunnel traffic to `localhost`, so every tunnel request looks like it's from `127.0.0.1` regardless of the real caller.
- **Session cookie**: `itsdangerous.URLSafeSerializer` (not `URLSafeTimedSerializer` - no server-side expiry check). Session length is enforced purely by the cookie having no `Max-Age`/`Expires` set, so it's a true browser-session cookie (dies when the browser fully closes), per a deliberate product decision to not have long-lived "remember me" sessions. Flags: `httponly=True`, `samesite="lax"`, **`secure=False`** - the last one is deliberate, not an oversight: the app is reached over plain HTTP on the LAN as well as HTTPS via the tunnel, and `secure=True` would silently break LAN login since the browser would refuse to send the cookie over plain HTTP.
- **No CSRF token** - not an oversight either. `SameSite=Lax` doesn't attach the cookie to cross-site `POST`s (only top-level `GET` navigations), and `/login`/`/logout`/`/fetch-order` are all `POST`. CORS `allow_credentials` is unset, so a cross-origin page can't read authenticated `GET` responses either.
- **Logout is client-side cookie deletion only** - there's no server-side revocation list. A captured token remains valid until the browser closes or `SESSION_SECRET_KEY` is rotated. **If a leak is suspected, the fix is: rotate `SESSION_SECRET_KEY` and restart the process** - that invalidates every existing session at once.
- **Cross-origin cookie scoping is expected, not a bug**: the LAN IP (`http://<pc-ip>:8000`) and the tunnel hostname (`https://...`) are different origins - logging in on one does not carry over to the other. Don't "fix" this later by accident.
- The static frontend mount (`/`) stays unauthenticated on purpose - the SPA shell itself isn't sensitive, it just won't get real data until `/me` succeeds. Only `/fetch-order`, `/confirm-order`, `/discard-proposal`, `/status`, `/branches` (and `/me` itself) require the session, via the `get_current_user` FastAPI dependency in `app.py`.
- `_state["started_by"]` records which staff member triggered the current/last run (set in `/fetch-order` from the authenticated user) - basic accountability given this tool spends real money, not a full audit log.

### Frontend (dashboard/frontend/src/App.tsx)

Single-component app: login form (if unauthenticated) → branch dropdown → "Fetch order" button → live progress (Phase A) → an **editable proposal review** once `stage === "proposal_ready"` → "Confirm & place orders" → live progress (Phase B) → four result tables (Missed / Needs Review / Altered-Split / full Product Mapping) rendered from `status.result` once `stage === "confirmed"`. No routing, no state library — all local `useState`.

**The proposal review** (`ProposalReview`/`ReviewItem` components) is the owner's full-control editing surface: per curated product, a row per allocation line with a `<select>` combining supplier+matched-product (options flattened from every candidate `gather_candidates` found, confident or not — a low-confidence one is labeled as such rather than hidden) and a qty `<input>`, plus add/remove-row controls. Local component state (`selections: Selection[]`) starts as a copy of the server's `proposed_allocations` and is freely edited client-side; nothing is sent back to the server until "Confirm & place orders" POSTs the whole edited set to `/confirm-order`. Closing the tab mid-review loses in-progress edits (the underlying proposal itself is safe on the server - see Backend) - a deliberate simplicity trade-off, not an oversight.

**Important gotcha if this is ever touched**: the effect that seeds `selections` from `status.proposal` is keyed off `proposal.proposal_id` (via a `useRef`) and only reseeds when that id actually changes - never on every routine 1.5s poll of the *same* still-pending proposal. Removing that guard would silently wipe out the owner's in-progress edits every second and a half, since the same `proposal_ready` stage can persist for hours.

Two mount effects, deliberately separate: one runs once and calls `GET /me` to decide `authenticated` (null while checking, then true/false); the second depends on `[authenticated]` and only starts polling once `authenticated === true`. **The polling mechanism itself must not be touched independent of this gating** - it's deliberately continuous and shared, not per-action: every tab/device polls `/status` every 1.5s from mount for as long as it's open, regardless of whether that tab is the one that clicked "Fetch Order" - since the backend state is global (see Backend above), this means every open viewer (different tabs, different devices) shows the same live phase/log/result simultaneously. A `visibilitychange`/`focus` listener also forces an immediate poll when a tab becomes active again, since Chrome throttles `setInterval` in backgrounded tabs (confirmed empirically: an unfocused tab can drop to 0 polls until refocused). `poll()` also doubles as the "is my session still valid" check for the whole session, not just at mount - a `401` response flips `authenticated` back to `false` and shows the login form again, rather than erroring on a stale/null status.

### Config (`order_automation_v2/config.py`)

Central place for env vars, branch credentials, supplier list/priority, and the supplier→Retailio-distributor-name mapping. Changes to supplier priority, branch credentials, or which Retailio distributor rows map to which supplier all happen here, not scattered across the pipeline.

Two separate supplier lists, not one — easy to conflate:
- **`CRM_SUPPLIERS`** (3 entries: DRK / A.K.Pharma / Mahaveer) — real-world vendor accounts as the CRM knows them. Used only by `crm.py`/`curated_list.py`, in Phase A's CRM-fetch/curate-list steps.
- **`SUPPLIERS`** (4 entries — A.K.Pharma split into `A.K.PHARMA (OUTSTATION)` / `A.K.PHARMA (DAVANGERE)`) — Retailio distributor tabs to open and match/allocate against, used in both phases (Phase A's `gather_candidates`, Phase B's `commit_selections`). The split exists because Retailio surfaces A.K.Pharma's two distributor accounts as separate catalogs with independent stock and independent hidden per-order limits; treating them as one combined tab (ticking both distributor checkboxes at once, the old behavior) made the same product show up twice under near-identical names with no way to fall back from one to the other when one hit a hidden cap. `SUPPLIER_DISTRIBUTOR_NAMES` keys must match `SUPPLIERS` exactly (one distributor name per entry now, not a list of two for A.K.Pharma).
